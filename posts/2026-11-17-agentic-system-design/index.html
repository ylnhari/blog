Agentic System Design: Every Pattern, and How to Choose

By ylnhari · November 17, 2026 · agents, llm, system design, architecture

Read the agent design guides from Google, Anthropic, Microsoft and OpenAI back to back and you will meet well over a dozen pattern names: sequential, coordinator, swarm, magentic, maker-checker, evaluator-optimizer, handoff, ReAct, and so on. They look like a long list to learn. They are not. Under different names, the guides describe about a dozen shapes, and every one of those shapes is the answer to the same three questions.

Who decides the next step: your code, or the model? What does each model call get to see? Who is allowed to change the world? Answer those three for your workload and the pattern falls out. Answer them badly and no framework will save the design. This post lays out all the patterns as one family, then spends most of its length on the parts that decide whether a design actually works in production: context, tools, long runs, safety, protocols and evals. It ends with a decision procedure and three worked designs.

Every figure here is a frame from an interactive page where you can click through each pattern, toggle context techniques and run a chooser that turns your requirements into a blueprint: Agentic System Design, Visualized.

Many pattern names, three decisions: who picks the next step, what each call sees, and who may act.

1. Start at the bottom of the ladder

Every guide opens with the same warning, and it is the most valuable sentence in all of them: do not build an agent if you do not need one. Anthropic's Building effective agents recommends the simplest approach that works and notes that agentic systems trade latency and cost for better task performance. Google's guide says predictable tasks, or ones a single model call can handle, may not need an agentic approach. Microsoft's tells you to use the lowest level of complexity that reliably meets your requirements. OpenAI's says that if a use case lacks complex decisions, hard-to-maintain rules or heavy unstructured data, a deterministic solution may be enough.

The ladder has four rungs, and the line that matters runs between the second and third:

  • A single model call. Summarise, classify, extract, translate. Good retrieval and a few examples often get you further than you expect.
  • A workflow. Anthropic's definition: LLMs and tools orchestrated through predefined code paths. Your code decides what happens next.
  • A single agent. The model directs its own process and tool use. The model decides what happens next.
  • Multiple agents. Several models, each deciding, coordinating with each other.

Moving from workflow to agent is the real architectural jump: you trade predictability for flexibility. Everything above that line needs evals, guardrails and observability that a workflow can mostly do without.

2. The one building block: a model, tools and instructions in a loop

OpenAI's guide names the three parts of any agent: a model for reasoning and decisions, tools to act and fetch context, and instructions that define behaviour and guardrails. Anthropic describes the running system as an LLM using tools in a loop based on feedback from the environment. Put together:

Three details in this picture decide most of an agent's behaviour:

  • Exit conditions. OpenAI lists them: a final-output tool call, a specific structured output, an error, or a maximum number of turns. Every loop needs a maximum. Without one, the cost of a confused agent has no ceiling.
  • The observation step. Whatever a tool returns lands in the context and steers the next decision. A tool that returns 40,000 tokens of raw logs, or text an attacker wrote, changes what the agent does next. Sections 6 and 9 return to this.
  • Guardrails sit on the edges, not in the prompt. Input checks, tool-call checks and output checks are code around the loop.

Every pattern that follows is either this loop, a few of these loops wired together, or a fixed workflow of single calls.

3. The twelve patterns, drawn as one family

Here is every pattern from the four guides, drawn the same way. Purple boxes are model calls, grey diamonds are code, teal boxes are tools, amber is a person. The badge in each card is the first design question: does code or the model pick the next step?

Code decides (workflows). These are cheaper, faster and easier to test, because the path is fixed.

  • Sequential chain. Fixed steps, each feeding the next, with optional code checks (gates) between them. Use it when the task splits cleanly into known steps. Avoid it when steps must change or loop back at runtime.
  • Router. One call (or a classic classifier) sorts the input, then code sends it down a dedicated path. Anthropic's examples: support queries split into refunds, technical and general; easy questions to a small model, hard ones to a large one.
  • Parallel sectioning. Independent subtasks run at once and code merges them. Use it when the subtasks are independent and latency matters. The hard part is reconciling outputs that disagree.
  • Voting. The same task runs several times and the answers are combined. It buys confidence, not speed. Watch for correlated mistakes: five copies of one model can be wrong together.
  • Loop or iterative refinement. A fixed sequence repeats on shared state until a quality threshold or an iteration limit is reached. Google names an infinite loop as its main risk and asks for a carefully designed exit: a maximum number of iterations or a target state.
  • Human in the loop. At predefined checkpoints the run pauses for a person to approve, correct or add input. It combines with every other pattern.

The model decides (agents). These handle work whose steps cannot be predicted, at the price of more calls and less predictability.

  • Single agent (ReAct). One model reasons, calls a tool, reads the result and repeats. Google, Microsoft and OpenAI all name it as the place to start once a workflow is not enough.
  • Orchestrator–workers. A lead model breaks the task down at runtime and hands pieces to workers, then synthesises. Anthropic's distinction from parallelization is the key: here the orchestrator chooses the subtasks for each input.
  • Hierarchical decomposition. Orchestrator–workers applied recursively, for large open-ended problems. Each level adds cost, latency and a place for errors to cascade.
  • Evaluator–optimizer. A generator produces, a critic checks against explicit criteria and sends feedback. Anthropic's condition for using it is worth memorising: clear evaluation criteria, and revisions that add measurable value.
  • Handoff. The active agent transfers the whole conversation, one way, to a better-suited peer. OpenAI calls this the decentralized pattern; Microsoft warns to avoid it when the right agent is obvious from the input, because a router is simpler.
  • Group chat or swarm. Several agents build on each other's work. In Microsoft's group chat, a chat manager picks who speaks next and suggests three or fewer agents. In Google's swarm, agents talk to each other and hand off work with no central coordinator; Google calls it the most complex and costly multi-agent pattern.

4. Same idea, different names

The naming is where most of the confusion comes from, so here is the map. If you read about "magentic orchestration" in Microsoft's guide and "coordinator" in Google's, they are close cousins of Anthropic's orchestrator–workers. Microsoft's maker-checker loop is Google's review-and-critique and Anthropic's evaluator–optimizer.

The mappings are approximate, and the differences are informative. Microsoft's magentic manager keeps an explicit task ledger of goals and subgoals it revises as it goes. OpenAI's manager calls other agents as tools and keeps control of the conversation, while its handoff gives control away. That last distinction matters: with a manager, one agent owns the user conversation; with handoffs, ownership moves.

5. When to split into multiple agents

This is where the guides stop being unanimous, and where the most expensive mistakes are made. Two widely read posts appeared a day apart in June 2025. Cognition's Don't Build Multi-Agents argued for a single-threaded agent, and Anthropic's How we built our multi-agent research system reported a large win from many agents. Both are right, about different work.

Anthropic's numbers show what parallel reading buys. A multi-agent setup with a Claude Opus 4 lead and Claude Sonnet 4 subagents outperformed single-agent Opus 4 by 90.2% on their internal research eval, and parallelism cut research time by up to 90% on complex queries. The cost is just as clear: agents use about 4× the tokens of a chat, and multi-agent systems about 15×. On their BrowseComp analysis, token usage alone explained 80% of the variance in performance. In other words, much of the multi-agent gain comes from spending more tokens in parallel, clean contexts.

Cognition's example shows what parallel writing costs. Split "build a Flappy Bird clone" between two subagents and one builds a Super Mario–style background while the other builds a bird that does not fit it. Their principle: every action carries implicit decisions, and agents that cannot see each other's decisions make conflicting ones. Anthropic draws the same boundary from the other side: domains where agents must share context or depend on each other heavily are poor fits, and most coding tasks have fewer parallelizable parts than research.

Ten months later, Cognition's follow-up, Multi-Agents: What's Actually Working, lists what now works in production: reviewer loops, a strong primary model consulting a stronger peer (it did not work when the primary was weaker), and a manager delegating to child agents, with read-only search subagents still the most common case. What still does not work: parallel-writer swarms and unstructured agent networks. Their rule is that writes stay single-threaded while extra agents contribute intelligence rather than actions. In short:

Parallelise reading and exploring. Keep the writes single-threaded.

OpenAI gives a second, more mechanical trigger for splitting: tool overload. The issue is overlap more than count. Their guide notes some agents handle more than 15 well-defined, distinct tools, while others struggle with fewer than 10 overlapping ones. Improve tool names and descriptions first. Split only if that does not fix it.

6. Context engineering is the actual job

Once a design is chosen, almost everything that goes wrong traces back to what the model saw on a given turn. Anthropic's Effective context engineering for AI agents frames it as an attention budget. Recall degrades as the window fills, an effect known as context rot, so every token has a cost even when it fits. Their guiding principle is to find the smallest set of high-signal tokens that maximises the chance of the outcome you want.

Five techniques do most of the work, and each removes a different kind of bloat:

  • Just-in-time retrieval. Keep references (file paths, saved queries, links) and load content through tools only when needed. Claude Code uses a hybrid: it loads its CLAUDE.md files up front and greps the codebase on demand.
  • Clear old tool results. A tool output that has already been acted on is rarely needed again. This is the lightest form of compaction.
  • Compaction. Near the limit, summarise the history and continue from the summary. Keep decisions, open bugs and implementation details; drop redundant output. Tune for recall first, then precision.
  • Structured notes. The agent writes progress to a file outside the window, such as a to-do list or NOTES.md, and reads it back later.
  • Sub-agents. Exploration happens in a clean window, and only a condensed summary comes back, often 1,000–2,000 tokens. This is why read-only subagents work: they spend tokens where it does not pollute the main context.

Anthropic's rule of thumb for choosing: compaction for long back-and-forth work, notes for iterative work with milestones, sub-agents for research that benefits from parallel exploration. The same post covers the static part of context. Write system prompts at the right "altitude": neither brittle if-else rules nor vague encouragement. Use a few diverse, canonical examples rather than a list of every edge case.

7. Tools are an interface for a new kind of user

Anthropic's original agents post makes a claim that holds up well: invest as much in the agent–computer interface as you would in a human–computer interface. Their follow-up, Writing effective tools for agents, turns that into concrete rules:

  • Build tools for tasks, not endpoints. A single schedule_event that finds availability and books beats separate list-users, list-events and create-event tools. A search_logs that returns relevant lines beats a read_logs that returns everything.
  • Namespace related tools, for example asana_projects_search, so the agent can tell similar tools apart.
  • Return meaning, not identifiers. Names and types help a model reason; opaque UUIDs do not. Offer a concise or detailed response format when IDs are needed later.
  • Be token-efficient by default. Paginate, filter and truncate, and say how to narrow the search when you truncate. Claude Code caps tool responses at 25,000 tokens by default.
  • Make errors actionable. "Invalid date, use YYYY-MM-DD" teaches the agent; a stack trace does not.
  • Poka-yoke the arguments (this one is from the original Building effective agents post). Change the interface so mistakes are hard to make. Anthropic's example: their coding agent broke when it changed directory and used relative paths, so they required absolute paths and the problem went away.

The method behind all of it is evaluation-driven. Prototype the tool, run realistic multi-step tasks, read the transcripts, then let an agent rewrite the descriptions. Anthropic reports that a tool-testing agent rewriting flawed tool descriptions cut task completion time by 40% in their research system.

8. Long runs: keep memory in files, not in the context

Some tasks take hours and outlive any single context window. Each new session starts with no memory of the last. Anthropic's Effective harnesses for long-running agents found three typical failures. The agent tries to one-shot everything and runs out of context halfway. It sees existing progress and declares the job done. It marks features complete without testing them end to end. Their fix borrows from how human engineers hand over a shift:

  • A one-time initializer session expands the request into a structured feature list (over 200 items for their claude.ai clone, all marked failing), writes a script that starts the app, creates a progress log and makes the first commit.
  • Every later coding session starts by reading the progress log, git history and feature list, and runs a basic end-to-end check. It then works on one feature, tests it as a user would, flips only that feature's pass flag, commits and writes a progress note.

The general lesson goes beyond coding: durable state belongs in files, databases and version control, where it survives a context reset, a crash or a deploy. Anthropic's research system follows the same idea in production. It saves the lead agent's plan to memory, resumes from the point of failure rather than restarting, and uses rainbow deployments so that updates do not break agents that are already running.

9. Safety is an architecture decision

An agent reads things you did not write: web pages, emails, issue comments, tool outputs. Any of them can contain instructions, and models cannot yet reliably tell data from commands. Simon Willison's lethal trifecta turns that risk into a design check: if one agent has access to private data, exposure to untrusted content and a way to communicate externally, an attacker can make it leak the data. He calls guardrail products that catch 95% of attacks a failing grade, so the reliable fix is structural: remove one of the three.

Inside whatever the trifecta leaves you, layer the defences. OpenAI's guide suggests:

  • Relevance and safety classifiers on input, to catch off-topic requests, jailbreaks and injections.
  • Moderation of harmful inputs, and PII filters and output validation on the way out.
  • Rules-based checks such as blocklists, length limits and regex.
  • Tool risk ratings. Rate each tool low, medium or high, based on read-only versus write, reversibility, permissions and financial impact. High-risk calls trigger extra checks or a person.

Their human-escalation triggers are the two to build first: the agent exceeds a failure threshold, or it is about to take a sensitive, irreversible or high-stakes action. Microsoft adds the enterprise basics: least privilege, audit trails, authenticated inter-agent calls, and security trimming so an agent never returns data the user could not access themselves.

10. MCP for tools, A2A for other agents

Two open protocols now cover the two kinds of connection an agent makes, and a design should know which one it is using.

  • The Model Context Protocol (MCP) connects an agent to tools and data. In the specification, a host application runs one client per server, and servers expose tools (functions the model calls), resources (data) and prompts (templates). The spec is explicit that tool descriptions from untrusted servers should be treated as untrusted, which is the trifecta again.
  • Agent2Agent (A2A) lets one agent delegate to another whose insides it cannot see. A remote agent publishes an Agent Card at /.well-known/agent-card.json describing its skills, endpoint and authentication. Work happens as a task that moves through states. The specification lists completed, failed, canceled and rejected as terminal states, and input-required and auth-required as interrupted ones. That pause is how a long-running remote agent asks for approval or more information. Version 1.0 was frozen on March 12, 2026, according to the Agentic AI Foundation's builder's guide.

The rule of thumb: if you control the other side and it is a function, make it an MCP tool. If it is someone else's agent with its own planning and its own tools, call it over A2A and treat it as opaque.

11. Evals: the only way to know a design works

Agents are non-deterministic, so one successful run proves little. Anthropic's Demystifying evals for AI agents gives the vocabulary:

  • A task with success criteria.
  • Several trials per task, because outputs vary between runs.
  • Graders: code, a model or a human.
  • The transcript of every call.
  • The outcome, meaning the actual final state, such as whether the booking exists in the database, rather than whether the agent said it booked it.

The single most useful idea in it is the difference between two metrics. pass@k is the chance that at least one of k tries succeeds. pass^k is the chance that all k succeed. At 75% per try, three tries give at least one success 98% of the time, but all three succeed only about 42% of the time. A coding assistant whose user can retry lives on pass@k. A customer-facing agent that must get it right every time lives on pass^k. Measure the one your product actually needs.

The guide's roadmap is refreshingly small:

  • Start early, with 20–50 tasks taken from real failures.
  • Grade outcomes rather than exact paths.
  • Calibrate LLM judges against people.
  • Read transcripts, so you know whether a failure is the agent's fault or the grader's.
  • Graduate capability evals the agent now passes reliably into a regression suite.

Anthropic's research team made the same point from experience: with large effect sizes, about 20 real queries were enough to see whether a change helped. In production, add full tracing of every decision and handoff. Microsoft also recommends timeouts, retries, circuit breakers and checkpoints, so one slow or failing agent degrades the run instead of hanging it.

A demo shows that an agent can succeed. pass^k shows whether it does, every time.

12. The design procedure

Put together, the guides imply one decision tree. Walk it from the top and stop at the first leaf that fits:

  1. Can one model call do it? Spend real effort on the prompt, retrieval and examples before answering no.
  2. Are the steps known in advance? If yes, build a workflow. Fan out if the steps are independent, chain them if they are not, and put a router in front if the inputs fall into distinct groups.
  3. Can one agent hold the job? One domain, a manageable set of distinct, well-described tools, and a task that fits in one context with compaction. If yes, build a single agent and invest in its tools and context.
  4. Is the extra work mostly reading in independent directions? If yes, use an orchestrator with parallel, read-only workers that return condensed findings. Go hierarchical only for very large problems.
  5. Does the conversation pass through distinct domains, one at a time? If yes, use specialist agents with handoffs. Use a router instead if the domain is clear from the first message.
  6. Otherwise, keep one writer. Give it read-only helpers for search and review, so every write comes from a single context.

Then, wherever you landed, add what the requirements demand:

  • An evaluator loop with a round cap, for strict and checkable quality criteria.
  • A human gate on high-risk tools, for irreversible or expensive actions.
  • A harness with progress files, compaction and checkpoints, for long runs.
  • A cut leg of the trifecta, when private data, untrusted input and external communication meet.
  • pass^k evals before launch, when users need the agent right every time.

13. Three systems, designed with the tree

The same procedure gives three very different architectures, because the work differs.

Customer support. The steps are not fixed, but the inputs fall into clear groups and each group is a small domain.

  • A cheap router sends each request to a specialist single agent with a few tools for its domain.
  • Refunds above a limit and cancellations go through a human gate.
  • Guardrails check relevance and personal data on the way in and out.
  • Reliability is measured with pass^k on real tickets.

Deep research. The work is exploring many independent directions, which parallelises well.

  • A lead agent plans and saves the plan to memory.
  • It sends read-only search workers out in clean contexts, more of them for harder questions, and synthesises what they return.
  • A final pass attaches citations.

Anthropic's prompts make the effort scale explicit. Simple fact-finding gets one agent with 3–10 tool calls; complex research can use more than 10 subagents. Early versions sometimes spawned 50 subagents for simple queries, which is why the rules exist.

Coding agent. Every edit carries implicit decisions, so the tree ends at "keep one writer".

  • A single coding agent does all the writing.
  • Read-only sub-agents search the codebase and the web.
  • A reviewer with a fresh context critiques each diff. Cognition reports their reviewer finds about 2 bugs per pull request, and works best when it starts without the writer's context.
  • For long tasks, the harness from section 8 keeps the feature list, progress notes and commits.
  • Shell commands and pushes sit behind a permission gate.

None of the three uses a swarm, and only one uses parallel agents. That is typical. Most production systems are a workflow or a single agent with excellent tools and context. A small part of them is multi-agent, and that part is almost always read-only.
