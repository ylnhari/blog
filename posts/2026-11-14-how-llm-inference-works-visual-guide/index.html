How LLM Inference Works: A Visual Guide to the Core Concepts

By ylnhari · November 14, 2026 · llm, inference, transformers, visualization

Every time you send a message to a chatbot, a large language model (LLM), made of billions of numbers, writes the reply one small piece at a time, and it runs all of those numbers again for every piece. Doing that for millions of people at once, quickly, and without spending a fortune on hardware, is one of the hardest engineering problems in AI right now. The name for it is inference: running a trained model to get answers out of it.

Most explanations of inference go straight to the jargon: KV cache, tensor parallelism, FlashAttention. Each term makes sense once you can picture what is happening inside the model, and almost none of them show you that. This guide works the other way round. Every idea starts as a picture, and the words come second.

By the end you will know:

  • what a language model is made of, piece by piece, and how text flows through it
  • how attention lets one word borrow meaning from the words before it
  • why writing a reply is slow, and why the limit is usually memory rather than arithmetic
  • the tricks that make serving cheaper: smarter batching, paged memory, lighter attention, smaller numbers, guessing ahead, and mixture-of-experts models
  • how a model too big for one GPU gets split across many, and what each kind of split costs
  • why training a model needs many times more memory than running it

You don't need a maths background beyond knowing roughly what a matrix is. Every figure here comes from an interactive companion page where you can click through each stage yourself: LLM Inference, Visualized.

Every trick that makes inference faster is really about where a block of numbers lives, and how often it has to move.

1. What is inside a language model

A language model has exactly one job: given the text so far, predict the next token. A token is a word or a piece of a word. Everything else is machinery for that single prediction. Here is the machinery, in the shape almost every modern model uses (GPT, Llama, Claude, Gemini, Mistral). Data flows from the bottom to the top:

In plain words:

  • The tokenizer cuts text into tokens and gives each one an ID number.
  • The embedding swaps each ID for a list of numbers, a vector, that the rest of the model can work with.
  • Then comes a block, repeated many times, which does two things. Attention lets each token gather information from the tokens before it. The MLP (multi-layer perceptron, a small network inside each block) then processes each token on its own. Each step adds its result to a running total called the residual stream, rather than replacing it.
  • At the top, the LM head (language-model head) scores every word in the vocabulary, and the best candidate becomes the next token. That token is appended to the input, and the whole model runs again.

That last loop is the heart of inference. One reply of 500 tokens means running the whole model 500 times, in order, because each new token depends on the one before it.

Attention, the one place where words talk to each other

Take the sentence "The animal didn't cross the street because it was too tired". What does "it" refer to? Attention is how the model works this out. Each token makes three vectors from its own embedding:

  • a query: what am I looking for?
  • a key: what do I contain?
  • a value: what will I pass on?

The query of "it" is compared with the key of every earlier word. A step called softmax turns those match scores into shares that add up to 100%. The best matches get the biggest share, and the new vector for "it" becomes a weighted mix of their values:

A model runs many of these lookups side by side, called heads. Each head has its own query, key and value weights, so each learns to look for something different: one might link pronouns to nouns, another might focus on the previous word. Words in the future are hidden, because a model that predicts the next word cannot be allowed to peek at it.

2. Three letters you will see everywhere: b, s, h

Once text is inside the model, everything is a block of numbers with a shape. Here is the query block from attention, drawn in 3D and cut into one slice per head:

Nearly every paper about LLM systems writes the main block as [b, s, h]:

  • b is the batch: how many separate conversations are processed together.
  • s is the sequence length: how many tokens each one has.
  • h is the hidden size: how many numbers describe one token.

Attention cuts h into the slices you saw above, one per head. Remember this cut: it is the same one that later splits a model across GPUs.

3. Why writing a reply is slow

Running a model happens in two very different phases. First, the whole prompt goes through at once. This phase is called prefill. All the prompt tokens form one big matrix, and the GPU's arithmetic units are kept busy:

Then the reply is written one token at a time. This phase is called decode. Each step multiplies a single row by the same full set of weights, which must be read from GPU memory again every step. The arithmetic is tiny, but the reading is huge, so the GPU spends most of its time waiting on memory:

To avoid recomputing the past at every step, the model saves each token's keys and values in a KV cache. The cache grows with every token and every conversation. A 7-billion-parameter model in 16-bit precision needs about 14 GB just for its weights, and one 4,096-token conversation adds about 2 GB of cache. Multiply that by dozens of users and memory runs out long before arithmetic does:

During decode, the GPU is not busy doing maths. It is busy fetching numbers from memory.

Almost every optimisation that follows attacks one of two costs you have just seen: reading the weights again for every token, or storing the KV cache for every conversation.

4. Serving many people at once

If decode spends its time reading the weights, the obvious fix is to make each read count for more. Put several conversations in one batch, and every read of the weights serves all of them at once. The catch is that replies finish at different times. In static batching, the whole batch waits for its longest reply, and finished slots sit empty. In in-flight batching (also called continuous batching), a finished conversation leaves straight away and a waiting one takes its slot on the next step:

Batching only helps if there is room in memory for many KV caches. Older servers reserved one long, unbroken stretch of memory per conversation, sized for the longest reply it might write. NVIDIA's example: a model with a 2,048-token limit reserves room for all 2,048 tokens even when the reply is short, and the unused part is wasted. PagedAttention borrows an idea from operating systems. It cuts the cache into small fixed-size blocks, hands them out only as tokens arrive, and keeps a table of which block lives where, so a conversation's blocks need not sit next to each other:

Less waste per conversation means more conversations fit, which means bigger batches, which means each read of the weights does more work. Serving engines such as vLLM and TensorRT-LLM use both ideas.

5. Making attention cheaper

The KV cache holds a key and a value for every head. But the heads do not each need their own. In grouped-query attention (GQA), several query heads share one key head and one value head, so the cache shrinks by the size of the group. Multi-query attention (MQA) is the extreme case, where every query head shares a single key and value head. Llama 2 70B is one well-known model that uses GQA:

Sharing heads costs a little quality, and an existing model can be converted rather than retrained: NVIDIA notes that turning a model into MQA needs fine-tuning on about 5% of the original training volume.

The second cost in attention is less obvious. Standard attention builds the full table of scores, one for every pair of tokens, and writes that table to the GPU's large but slow main memory (HBM) and reads it back. For long inputs that table is enormous. FlashAttention never builds it. It works on one small tile at a time inside the GPU's tiny but very fast on-chip memory (SRAM), keeping a running total so the softmax still comes out exactly right:

The maths is the same, and so is the answer. What changes is how many times data crosses the slow path to main memory. That is the theme of this whole guide again.

6. Making the model smaller

Fewer bytes per weight means less to read on every decode step and more room for the KV cache. There are three common ways to get there.

Quantization stores each number with fewer bits. Models are usually trained with 16 or 32 bits per value, but most can be represented with eight or even fewer. Each weight snaps to the nearest of a small set of levels:

Weights are the easy part, because they are fixed after training. The values flowing through the model are harder, because they contain occasional very large outliers. One outlier stretches the scale, and every other value loses precision. Much of the research in this area is about handling those outliers.

Sparsity sets some weights to zero. Random zeros barely help, because the GPU still has to check every position. But recent NVIDIA GPUs have hardware for one fixed pattern: two zeros in every group of four. The zeros are dropped from storage, a small index records where the survivors were, and the hardware skips the missing work:

Distillation trains a smaller student model to copy a larger teacher. The trick is to learn from the teacher's whole spread of guesses rather than only the right answer. "Mat" is correct, but "rug" being a close second carries information too. The classic result is DistilBERT, which compresses BERT by 40% while keeping 97% of its language understanding, and runs 60% faster:

7. Guessing ahead

Decode is slow because each token waits for the one before it. Speculative decoding gets around that. A small, fast draft model guesses the next few tokens. The big model then checks all the guesses in a single pass, which costs about the same as producing one token, because the weights are read once either way. It keeps the guesses up to the first wrong one, and adds its own token at that point:

The output is exactly what the big model would have written on its own. When the draft guesses well, several tokens come out of each pass of the big model. When it guesses badly, you lose a little time on the draft and nothing else.

Every technique so far either reads fewer bytes, stores fewer bytes, or gets more tokens out of each read.

8. When one GPU is not enough

At two bytes per number, a 70-billion-parameter model is 140 GB of weights, already more than a common 80 GB data-centre GPU holds, before any KV cache. So big models are split across several GPUs. There are a few ways to make the split, and each answers the same question: which dimension of which block gets cut, and what has to travel between GPUs as a result?

The simplest is data parallelism: copy the whole model onto every GPU and send different conversations to each. It multiplies throughput and needs no communication, but it only works if the model fits on one GPU in the first place:

Pipeline parallelism gives each GPU a slice of the layers, like an assembly line. With four stages, each GPU holds a quarter of the weights. The problem is waiting: GPU 3 has nothing to do until GPU 0 has finished. Splitting the batch into smaller microbatches keeps more stages busy at once, but the idle "bubble" at the start and end never fully goes away:

Pipelining helps a model fit and adds throughput once the pipeline is full. It never makes a single request faster.

Tensor parallelism splits the weight matrices inside every layer, so all GPUs work on every token together. It rests on one neat trick. Split the MLP's first weight matrix by columns and the second by rows. Each GPU can then do both multiplications on its own half, with no talking in between, and one combining step at the end (an All-Reduce) adds the halves up:

That combining step happens twice in every layer, so tensor parallelism needs the very fast links found inside one server. Real systems mix the methods: tensor parallelism inside a server, pipeline parallelism across servers, and data parallelism to add more copies for more users. 9. The copies tensor parallelism leaves behind

Tensor parallelism has a blind spot. Between the split blocks, every GPU holds the same full block of activations (the in-between numbers that flow from one layer to the next) and runs the same normalisation step on it. The same data, stored twice:

Normalisation treats each token on its own, so the fix is to cut that block along the sequence instead: each GPU handles half the tokens. This is called sequence parallelism, and it removes the copies without adding any communication:

The research that introduced this pairing reports that, together with smarter recomputation, it cuts activation memory by 5×.

10. Mixture of experts: a bigger model for the same work

One more trick changes the model itself. In a mixture-of-experts (MoE) model, the single MLP in each block is replaced by several smaller MLPs, called experts, plus a tiny router that picks a few experts for each token. Every other expert sits idle for that token:

Mixtral 8×7B is the well-known example: it has eight experts per block and uses two of them for each token, so it stores 46.7B parameters but uses only 12.9B per token. That split matters for serving. The memory you need follows the total, because every expert has to be loaded. The work per token follows the active part, so a token costs about what a much smaller model would. When the experts no longer fit on one GPU, they are spread across several. That is expert parallelism, the fifth way to split a model, and it needs its own communication step to send each token to the GPU that holds its experts.

11. Why training needs so much more

All of that stored activation memory is mostly a training problem. To learn, a model runs backwards through every layer, and each step backwards needs the numbers that went into that layer on the way forward. Training also stores gradients and optimiser state for every weight. Running a model forward only needs the weights and the KV cache:
