How LLM Inference Works: A Visual Guide to the Core Concepts

By ylnhari · November 14, 2026 · llm, inference, transformers, visualization

Most explanations of LLM inference optimization are written in prose and formulas: "tensor parallelism splits the weight matrices", "sequence parallelism partitions LayerNorm along the sequence dimension", "the KV cache grows linearly with batch and sequence length". Each sentence is correct, and each one hides the same thing: a tensor with a shape, sitting on a particular piece of hardware.

Once you can see that shape, these techniques stop being a list to memorise and become variations on one question: which slice of which tensor lives where, and what does moving it cost? This guide builds that picture from scratch. It starts with the shapes inside a transformer, then shows what each technique from NVIDIA's Mastering LLM Techniques: Inference Optimization does to them. Every inference optimization is a statement about which tensor shape lives on which piece of hardware.

Step 1: learn three letters before anything else

Almost every paper on LLM systems writes activations as [b, s, h] and assumes you know what that means. Here is what each letter is:

  • b: the batch, meaning how many sequences are processed together.
  • s: the sequence length, meaning tokens per sequence.
  • h: the hidden size (d_model), meaning how many numbers represent one token.

Part I of the page traces one batch from raw text to the next token. Token IDs [b, s] become embeddings [b, s, h]. These are projected into Q, K and V, and Q is cut into heads, [b, n_heads, s, d_head] with h = n_heads × d_head. Then RoPE rotates each head's q and k by position, so word order counts, and each head builds an [s × s] score matrix. Next, the MLP widens to [b, s, ffn] and back, and the LM head produces [b, s, V]. A toggle swaps the toy sizes for real Llama 2 7B numbers.

Once you have watched Q split into heads, tensor parallelism stops being abstract. It is the same cut, with the heads sent to different GPUs.

Step 2: why models get split across GPUs, and the four ways to do it

Weights alone outgrow a GPU quickly. A 70B-parameter model at 2 bytes per parameter is 140 GB, already more than one 80 GB GPU holds, and that is before any KV cache. A 405B model is 810 GB. So parallelism first exists to make the model fit. It also serves two other goals, more throughput and lower latency, and each strategy helps only some of the three.

Every strategy answers one question: which dimension of which tensor gets cut, and what has to travel between GPUs as a result?

  • Data parallelism copies the whole model and splits the batch b. Throughput scales almost perfectly and GPUs never talk at inference, but it is useless if the model does not fit on one GPU.
  • Pipeline parallelism splits the stack of layers. Each GPU holds a slice of the layers and passes a small [b, s, h] activation to the next. It helps a model fit, but one request still walks through every stage in turn, and stages idle while they wait.
  • Tensor parallelism splits the weight matrices inside every layer: attention by heads, the MLP by columns then rows, the embedding and LM head by vocabulary. Every GPU works on every layer for the same sequences, which makes each request faster. The price is communication inside every layer.
  • Sequence parallelism splits what tensor parallelism leaves copied (Step 3).

Tensor parallelism rests on one neat trick. Split the MLP's first weight by columns and the second by rows. Each GPU can then run both matmuls and the nonlinearity between them on its own half, and a single All-Reduce at the end adds up the partial results:

That All-Reduce happens twice in every layer, so tensor parallelism needs the fast links inside one server. Real deployments therefore mix strategies: tensor parallelism within a server, pipeline parallelism across servers, and data parallelism to add replicas for traffic. The interactive page walks through each one, and how they combine on a 16-GPU cluster.

Step 3: why splitting along s saves memory when splitting along h already did

A natural objection to sequence parallelism: whether a GPU holds all the tokens or half of them, the total data is the same, so where does the saving come from? The answer is in what tensor parallelism leaves behind. Inside attention and the MLP, tensor parallelism cuts along h, so each GPU holds [b, s, h/2] and nothing is duplicated (image at the top). Between those blocks, an All-Reduce leaves every GPU with the full [b, s, h]. LayerNorm then needs each token's whole h-vector to compute a mean and variance, so it can't be cut along h. Each GPU therefore stores a complete copy.

The total unique data really is the same. The waste is that with two GPUs it is stored twice. LayerNorm treats each token on its own, though, so you can cut along s instead:

In the page's simplified unit count, one layer comes to 12 units on one GPU, 9.5 per GPU with TP=2, and 6.0 per GPU with TP and sequence parallelism. Communication doesn't grow either. An All-Reduce is a Reduce-Scatter followed by an All-Gather, and sequence parallelism simply runs the cheap per-token ops in between. The paper behind this, Reducing Activation Recomputation in Large Transformer Models, reports that its two techniques together reduce activation memory by 5× and cut the execution-time overhead of activation recomputation by over 90%.

The total data is the same. Replication is what you pay for.

Step 4: put real numbers on memory

Inference is mostly a memory problem. The NVIDIA post works through two figures, and the page lets you move them. A 7B model in FP16 needs about 14 GB for its weights. The KV cache costs batch × seq × 2 × layers × hidden × bytes, which for Llama 2 7B at batch 1 and 4,096 tokens is about 2 GB. Step 5: understand why training needs so much more

The activation-memory problem in Step 3 is really a training problem. The backward pass needs the input that went into every layer, because every weight gradient is the saved input transposed times the incoming gradient.
